# I.L.X — межсетевой шлюз Reticulum ↔ Meshtastic

Версия: v2
Статус: черновик спецификации прототипа. Значения, помеченные как «проверить», нужно сверить с документацией и исходниками перед реализацией.

Документация Meshtastic: https://meshtastic.org/docs/overview/

## 1. Цель

Приложение-шлюз, через которое пользователь Reticulum может отправлять текстовые сообщения пользователю Meshtastic и наоборот. Шлюз связывает сети на уровне приложения. Он не заменяет и не изменяет адресацию самих сетей.

## 2. Ключевые решения

- **Прокси, а не сквозная связь.** Шлюз принимает сообщение, извлекает содержимое и создаёт новое сообщение средствами сети-получателя. Шлюз является доверенной точкой и видит содержимое.
- **Адресация уровня приложения.** Общего адреса, который обе сети понимают нативно, нет. Приложение хранит собственный постоянный ID контакта и таблицу соответствий.
- **Перевод на уровне сообщений, а не пакетов.** Побайтная пересборка пакетов не используется. Шлюз работает с содержимым сообщения и метаданными.
- **Только текст в первой версии.** Остальные типы добавляются по одному, с отдельным проектированием формата и ограничений.
- **Явность.** Шлюз не создаёт впечатления успешной доставки, если функция не поддерживается или доставка не подтверждена.

## 3. Модель контакта

Запись контакта хранится в приложении:

- `contact_id` — постоянный ID контакта приложения (например, UUID)
- `display_name` — отображаемое имя
- `lxmf_destination` — Reticulum/LXMF destination hash собеседника
- `meshtastic_node_id` — настоящий ID узла Meshtastic (32-битное число, вид `!xxxxxxxx`)
- `meshtastic_short_name` — короткое имя, только для отображения
- `capabilities` — флаги поддерживаемых функций на стороне контакта
- `verified` — подтверждено ли соответствие пользователем вручную

Связывание на первом этапе ручное. Короткие имена не используются как ключ.

## 4. Формат envelope между шлюзом и приложением

Каждое сообщение, которое проходит через шлюз, оборачивается в envelope:

- `v` — версия протокола envelope
- `type` — тип сообщения (см. раздел 5)
- `msg_id` — уникальный ID сообщения, создаётся на стороне отправителя
- `origin_network` — сеть исходного отправителя: `reticulum` или `meshtastic`
- `origin_author` — имя или ID автора на исходной сети
- `origin_signature` — опционально: подпись автора (см. раздел 8)
- `ttl` — счётчик переходов через шлюзы, защита от петель
- `payload` — содержимое сообщения

## 5. Типы сообщений

| Тип | Reticulum → Meshtastic | Meshtastic → Reticulum | Статус |
|---|---|---|---|
| `text` | да | да | первая версия |
| `delivery_report` | да | да | первая версия |
| `nodeinfo` | да (уведомление о контакте) | да | обсуждается |
| `position` | нет | нет | не в первой версии |
| `file`, `image`, `voice`, `call` | нет | нет | не в первой версии, отдельное проектирование |
| `command`, `script`, `remote_exec` | запрещено | запрещено | не пересылается автоматически |

Для `text` действуют ограничения размера. Полезная нагрузка Meshtastic примерно 230 байт (проверить по текущей версии). Длинные сообщения режутся на части с номером и общим `msg_id`. Сборка выполняется на стороне получателя, если он поддерживает фрагментацию. Если нет, шлюз отправляет отказ с причиной.

## 6. Обработка сообщений

1. Шлюз получает сообщение от одной сети.
2. Проверяет `ttl` и `msg_id` по списку недавно обработанных. Дубликаты отбрасываются.
3. Ищет получателя в таблице контактов. Если соответствия нет, отправляет отказ отправителю.
4. Проверяет, поддерживает ли получатель тип сообщения. Если нет, отправляет отказ с причиной.
5. Формирует новое сообщение средствами сети-получателя и отправляет его.
6. Ждёт подтверждения доставки, если оно доступно в этой сети. Иначе помечает статус как «отправлено, без подтверждения».
7. Уведомляет отправителя о результате.

## 7. Ошибки и отказы

Шлюз всегда сообщает отправителю один из статусов:

- `delivered` — получено подтверждение от сети-получателя
- `sent_unconfirmed` — отправлено, подтверждения нет
- `unsupported_type` — получатель не поддерживает этот тип
- `no_contact` — соответствие не найдено
- `too_large` — сообщение не поместилось, фрагментация не поддерживается
- `gateway_error` — внутренняя ошибка шлюза
- `loop_dropped` — отброшено из-за TTL или дубликата

Текст уведомления в интерфейсе должен прямо говорить, что статус не означает «прочитано».

## 8. Безопасность

- Шлюз получает сообщения в расшифрованном виде. Шифрование одной сети не защищает от шлюза.
- Имя автора, которое передаёт шлюз, не проверяется. Любой может указать любое имя.
- Опционально: автор подписывает текст своим Reticulum-ключом, шлюз передаёт подпись. Проверить подпись могут только участники Reticulum. У Meshtastic такого механизма нет, поэтому это ограничение нужно документировать.
- Сквозное шифрование до конечного пользователя и управление ключами вынесены за пределы первой версии.
- Команды, скрипты и удалённое выполнение не пересылаются автоматически.
- Для Meshtastic шлюз использует канал с известным PSK. Все участники канала видят сообщения, отправленные через шлюз. Тип отправки (широковещательная или прямая) задаётся явно. Возможности прошивки для прямых сообщений проверить отдельно.

## 9. План прототипа

1. Текстовая пересылка в обе стороны.
2. Ручное связывание контактов между LXMF destination и Meshtastic node ID.
3. Явная индикация межсетевого сообщения в интерфейсе.
4. Статусы доставки и отказов по разделу 7.
5. Фрагментация текста по необходимости.
6. Добавление других типов по одному.

## 10. Пример пакета Meshtastic

Пример взят из документации Meshtastic: пакет с позицией, отправленный в широковещательный канал.

```
from: 305419896
to: 4294967295
channel: 0
id: 2271560481
hop_limit: 2
hop_start: 3
priority: DEFAULT
relay_node: 18
rx_time: 1772514955
rx_snr: -1.5
rx_rssi: -105
decoded {
   portnum: POSITION_APP
   payload: "latitude_i: 480000000 longitude_i: 110000000 altitude: 0 time: 1772514893 location_source: LOC_MANUAL precision_bits: 15"
   bitfield: 1
}
```

Что здесь важно для шлюза:

- `from` — ID отправителя в виде десятичного числа. Это 305419896, то есть `0x12345678`. Для шлюза его нужно хранить как `meshtastic_node_id` в таблице контактов.
- `to` — адресат. Значение 4294967295 равно `0xFFFFFFFF`, это широковещательная отправка. Для прямого сообщения здесь будет ID конкретного узла.
- `channel` — индекс канала. Шлюз должен знать, какой канал использует для связи.
- `id` — ID пакета. Используется для защиты от дубликатов (раздел 6, шаг 2).
- `hop_limit` и `hop_start` — оставшиеся и начальные переходы. В примере пакет прошёл один переход (3 − 2 = 1). Это поможет в оценке TTL и петель.
- `relay_node` — последний байт ID узла, который ретранслировал пакет (проверить по документации, как именно он задаётся).
- `rx_time`, `rx_snr`, `rx_rssi` — локальные метаданные приёма на ноде, которая логирует пакет. Они не передаются по эфиру, поэтому в envelope не нужны.
- `priority` — внутреннее поле маршрутизатора, в эфир не уходит. В envelope его не переносим.
- `decoded.portnum` — тип содержимого. `POSITION_APP` означает позицию, для текста будет `TEXT_MESSAGE_APP`.
- `decoded.payload` — здесь показано в человекочитаемом виде. В эфире это protobuf-сообщение `Position` (поля `latitude_i`, `longitude_i` и др.). Для разбора нужны protobuf-описания из `meshtastic/protobufs`.
- `bitfield` — служебные флаги, которые зависят от версии прошивки.

Пример также показывает, что широковещательный пакет с позицией и текстом приходит одинаково. Для шлюза различие видно только по `portnum`.

## Итог обсуждения

**Что мы поняли:**
- Reticulum и Meshtastic нельзя напрямую соединить на уровне пакетов. У них разные адресные пространства, форматы, размеры и механизмы доставки.
- Рабочий вариант для прототипа — шлюз на уровне приложения, который принимает сообщение, извлекает содержимое и отправляет новое сообщение в сеть получателя.
- Адресация строится через таблицу контактов, которая связывает LXMF destination и Meshtastic node ID под постоянным ID приложения.
- Шлюз является доверенной точкой. Сквозной безопасности между пользователями разных сетей он не даёт.
- Поддержка функций различается. Текст реалистичен в первой версии. Звонки, файлы и картинки в Meshtastic практически не передаются из-за размера и скорости канала. Команды и удалённое выполнение не пересылаются.
- Реализация на Python. Meshtastic-часть работает через внешний процесс, который подключается к ноде по USB, TCP, BLE или MQTT. Reticulum-часть работает через RNS и LXMF.
- Собственный интерфейс Reticulum возможен в будущем, но начинать стоит с шлюза-приложения.
- Для анализа нужен уровень пакетов, а не эфира. Эфирный уровень понадобится позже, когда появится RNode.
